# CosyVoice3 首段 PCM 交付

RTX PRO 6000，TensorRT，无显式 seed，C4。使用已有两次服务计时和一次独立带 profiler 的诊断。脚本按客户端请求 ID 匹配 `CV3BEGIN` 的 offset=0，并在相邻调用之间查找唯一的 `CV3FLOW` 区间。正式轮次各有 16 个首块。首个 PCM 读的时刻用末次非空读、请求 E2E 和首包耗时近似还原，因此带有从末次读到 EOF 的误差。

| 基线 | 开始解码至首 PCM 均值 | 首块 Flow 主机调用均值 |
| --- | ---: | ---: |
| 第一次启动 | 230.9 ms | 36.3 ms |
| 第二次启动 | 220.9 ms | 35.1 ms |

在独立的四请求 Perfetto 里按时间顺序对齐了 19 次 `forward_streaming`、19 个 Flow 和 19 个 HiFT，检查线程时间线顺序与单调时钟相邻调用间距。首块 Flow、HiFT 的 CPU scope 均值分别是 36.8、28.8 ms，后续 15 块分别是 40.5、44.0 ms。CPU scope 包含子调用和等待，不代表 GPU 专属时间。

四个首块中，第一块单独交付给执行器，余下三块由同一个 `execute_context_3(75)` 处理。这三块各自结束 HiFT 到组执行结束还剩 136.9、66.3、0.1 ms；相应的组结束到客户端首 PCM 约 96、96、97 ms。单独执行的那个请求也在组结束约 212 ms 后才读到第一段 PCM。组内串行返回解释了部分等待。组结束后的间隔还包括下游处理、交付和客户端读；现有标记不能进一步归因。诊断轮 4 请求的分段时间独立于上表。

下一处值得打点的是 Stage 1 结果何时可交付、在下游何时被取走，以及 HTTP 何时写出首段。当前数据尚不足以估算提前交付或改声码器的服务收益。

## 首块从设备回传后，客户端还等多久

重读了普通流式 C4 和显式 seed C4 的 Stage 1 CPU/CUDA 时间线，结合已有的引擎、客户端计时。下表时间使用同一条请求的首块。按模型调用和 stream 13 的 D→H 事件顺序配对；普通流量 19 次调用对应 19 次回传，显式 seed 20 次对应 20 次。八个首块回传均为 69,120 字节。用每次 Flow 的内部起止计时限制两条时钟的偏移，两个 trace 的可行区间宽度分别为 0.258、0.325 ms。客户端首读时刻仍有前述 EOF 近似误差。

| 普通流量，按首块执行顺序 | 本组结束到回传完成 | 回传完成到客户端首 PCM | 紧接着的 Stage 1 模型执行时长 | 下一组结束到客户端首 PCM |
| --- | ---: | ---: | ---: | ---: |
| 单独执行的请求 | 0.51 ms | 211.3 ms | 207.3 ms | 3.3 ms |
| 三请求组中的第一个 | 0.36 ms | 95.7 ms | 81.2 ms | 13.9 ms |
| 三请求组中的第二个 | 0.38 ms | 95.4 ms | 81.2 ms | 13.6 ms |
| 三请求组中的第三个 | 0.39 ms | 96.5 ms | 81.2 ms | 14.6 ms |

显式 seed 的四个请求在这份记录中分别执行。首块后的下一次模型执行为空，CPU 区间都小于 0.1 ms；回传完成到首 PCM 为 2.5–4.4 ms。两种流量的生成与调度条件不同，这个对照只说明时间关系。

用另外两次关闭 torch profiler 的普通流量基线交叉检查，每次 4 波、每波 4 个请求。以该波**任意请求的第一条后续块开始解码**为时间零点，8 波中最早的客户端首读都出现在约 0.2–2.1 ms，其余 24 次首读出现在约 71.1–86.5 ms。这里没有 GPU 拷贝时间戳，不能用这两轮直接计算回传延迟。

这批数据把排查范围缩到 Stage 1 的结果交付：工作组结束后，首块数据迅速拷到主机；繁忙时，客户端读到这份数据往往已在下一次模型执行之后。记录中没有逐请求的引擎结果出队、API 收到模型输出、ASGI 首次 body 写出时刻。尚不能据此判定是哪一层延后转交，也不能把重叠的整段时间当成可节省的延迟。后续若做定点验证，在上述三个边界携带相同请求 ID 即可区分。
