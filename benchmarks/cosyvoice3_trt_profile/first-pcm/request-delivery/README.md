# CosyVoice 3 首块音频在哪一步等下一批

RTX PRO 6000，vLLM 0.34 的 MRv2 generation runner，单卡 TRT，流式 C4，普通采样，未指定 seed。一个服务实例预热两波，再采集两波，共 8 个正式请求。沿用此前无 seed 基线的部署和四条输入。只加主机打点和一次非阻塞 CUDA event 查询，保留原有调度顺序。

同一条请求的第一个非空波形返回后，Stage 1 提交 GPU→CPU 拷贝。两波中，引擎每次都先执行一组其他音频工作，才从容量为 2 的队列取出上一组结果。按请求 ID、Stage 1 进程和 FIFO 顺序交叉匹配，8/8 首块在取结果时拷贝事件都已就绪。

| 正式波次与首块所在批 | 请求数 | 提交拷贝到结果出队 | 其中下一组模型执行 | 本组模型结束到客户端首读 |
| --- | ---: | ---: | ---: | ---: |
| 第一波，单请求批 | 1 | 182.53 ms | 178.59 ms | 189.11 ms |
| 第一波，三请求批 | 3 | 78.56 ms | 73.45 ms | 87.42–88.51 ms |
| 第二波，单请求批 | 1 | 195.22 ms | 191.34 ms | 202.79 ms |
| 第二波，三请求批 | 3 | 78.57 ms | 72.97 ms | 85.53–86.37 ms |

四批中，下一组模型执行覆盖提交拷贝到出队间隔的 92.9%–98.0%。出队后组织好主机上的音频结果用了 0.08–0.13 ms，从这一步到同机 HTTP 客户端首读用了 5.89–9.20 ms。取结果时只检查一次 CUDA event；本轮没有测拷贝完成的精确时刻。此前的设备侧 trace 单独记录了那一轮的实际 D→H 完成时间。[历史设备时间线](../README.md)

这说明在这两波里，首包交付被下一批执行推迟。若要评价提前交付的净收益，可首先仅在 Stage 1 关闭异步调度做配置对照，核实实际收取顺序，再比较首包、音频秒/秒、RTF 和流式块间隔。此次没有更改调度或测量优化收益。各请求共享同批等待，不能把 8 行当成 8 次独立的排队样本。

## Perfetto 与复现

下载时间线，在 Perfetto 中打开。每个请求有独立轨道，展示从客户端发起到首读的分段。另有服务端进程的原始打点轨道。这份时间线使用同一台 Linux 主机的单调时钟。所有正式请求直到结束的服务端字段都保存在原始 JSONL 中。[Perfetto 时间线](delivery.perfetto.json.gz) · [原始主机打点](marks.jsonl.gz) · [客户端计时](requests.json) · [逐请求分段](summary.json)

运行 `python analyze.py` 可从两个归档输入重建汇总和时间线。采集代码依赖实验机原有的 TRT 计划、模型、参考音频和无 seed 基线启动目录。将 `collect.py` 和 `cv3_delivery_marks.py` 置于实验根目录下的独立子目录，运行 `python collect.py`。脚本校验源码挂载点、检查 GPU 占用，并在采集后停止本次容器。用 `python analyze.py <采集目录>` 提取正式波次。打点存在开销，这些数据用于归因。[采集脚本](collect.py) · [打点](cv3_delivery_marks.py) · [配对分析](analyze.py)
