# CosyVoice 3 流式首包与 Stage 1 调度

RTX PRO 6000 Blackwell 96 GB，单卡，vLLM 0.34，MRv2，TRT Flow。用同一模型、参考音频、四条文本和普通无 seed 采样，在 C4 下比较 Stage 1 的 `async_scheduling: true`（A）和 `false`（B）。Stage 0 在四次启动中均为 `OmniARAsyncScheduler`、队列容量 2。Stage 1 的启动打点确认 A 的容量为 2，使用 `step_with_batch_queue`；B 的容量为 1，使用 `step`。

按 A1 → B1 → B2 → A2 顺序独立重启。每次两波热身后测六波，每波四个同时请求，每种配置共 48 个正式请求。下表按各配置全部正式请求统计。

| 指标 | A，开启 | B，关闭 | 相对变化 |
| --- | ---: | ---: | ---: |
| 首包 P50（ms） | 526.0 | 472.5 | -10.2% |
| 首包 P95（ms） | 573.2 | 497.9 | -13.1% |
| 吞吐（音频秒/墙钟秒） | 18.58 | 18.59 | +0.0% |
| 平均请求 RTF | 0.209 | 0.208 | -0.3% |
| 平均请求端到端耗时（s） | 1.579 | 1.507 | -4.6% |
| 首块模型组返回至客户端首读 P50（ms） | 88.6 | 7.8 | -91.2% |
| 相邻音频块间隔 P95（ms） | 369.9 | 474.9 | +28.4% |
| 首块至第二块间隔 P95（ms） | 344.0 | 500.8 | +45.5% |
| 从第二块起相邻块间隔 P95（ms） | 372.2 | 367.0 | -1.4% |

在模型返回首块到客户端首读之间，A 有 48/48 个请求经历了另一组模型执行完毕，B 有 0/48 个。提前交付第一块后，到第二块的间隔随之拉长。按同机首块到达即播放、以实际块字节数按 24 kHz 单声道 PCM16 推算，出现缓冲耗尽的请求数为 A 0/48、B 0/48，最小剩余音频分别为 372、206 ms。这个推算把整块视为在读到首字节时可用，未模拟公网、客户端解码或真实播放器。

吞吐为所有响应的 PCM 秒数除以各正式波从首个请求出发到最后一个响应完成的耗时之和。RTF 是每个请求端到端耗时除以自身音频时长，再取均值。首包从发出请求计到首个 HTTP body 字节；块间隔按 HTTP chunk 首字节记录，保留了服务端 body 边界。百分位使用线性插值。普通采样允许生成时长变化，没有对齐输出内容或评估音质。结果只覆盖该卡、TRT 和 C4。

四份 Perfetto 均已用 trace processor 验证可读取。B2 有一个模型组的开始日志被两个进程的输出交错，时间线只标注已知的结束点。该请求的首包、组返回和全部 HTTP 块时间戳齐全。低延迟流式部署可使用这一已有开关；当前证据支持写成带适用范围的配置示例。

## 复现

在实验机的基线启动目录旁建一个新的同级子目录，放入采集脚本后运行 `python bench.py`。脚本复用现有 TRT 引擎、模型和无 seed 部署，两臂使用同样的计时打点。将 `CV3_REF_WAV` 指向同一参考音频可覆盖默认参考路径。在归档目录运行 `python analyze.py` 可离线重建汇总与四份 Perfetto；传入采集目录可从正式波次与服务端日志重建四份输入。时间线展示同机单调时钟上的 Stage 1 执行组和客户端 PCM 到达区间。[采集脚本](bench.py) · [分析脚本](analyze.py) · [完整统计](summary.json) · [此前逐请求的引擎出队诊断](https://github.com/EddieTzy/vllm-omni/tree/51420dec3593988903084ee02663ffe8e033784b/benchmarks/cosyvoice3_trt_profile/first-pcm/request-delivery)
